## On the work

The headline risk was the meta-guard being "robust by coincidence, not design."
The first implementation parsed pytest counts with unanchored regexes over the
whole captured stream and never checked the subprocess exit code. Cross-lineage
adversarial review (kimi was the rigorous one; the glm run truncated but raised
the same core points) caught this as a BLOCKER. The hardened version anchors
count parsing to the LAST summary line (the `in <n>s` timing suffix) and
requires exit_code==0.

The most valuable thing the review surfaced: when importorskip fires at MODULE
level and that file is collected in isolation, pytest exits 5 (no tests
collected) — so the exit-code branch is the PRIMARY signal, with the zero-pass
count as the version-independent backup. My first falsifier asserted
`match="importorskip"` and failed because exit-5 fired first; that failure was
correct behavior, not a bug. Fixed the assertion to accept either signal. Only a
live/run falsifier reveals this — the hand-written summary deny-tests all passed
but masked the real pytest semantics.

The deny-case discipline (process-calibration §5) carried the day again: every
guard is factored into a pure function with an explicit deny-case, so none are
tautologies. `test_require_gate_ran_ignores_count_like_test_output` and
`_rejects_nonzero_exit` directly encode the BLOCKER's failure modes.
