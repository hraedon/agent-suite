# 0B-PLAN.md — non-drafter adversarial review
**Reviewer:** ollama-cloud/minimax-m3 (lineage, non-drafter) · **Drafted by:** openai/gpt-5.6-sol · **Mode:** text only, no gate transition.
## VERDICT: **accept-with-changes**
The plan is structurally faithful to the frozen rubric, the §2.5 invariant map is genuinely complete, and the security core is correct. The honest residuals (single-operator estate, Developer-edition licensing, witness independence unproven) are stated. But there is one **structural hole** (single-operator estate cannot satisfy `INV-016` on a three-host lab) that the plan labels as "name the operators" rather than "declare simulated-independence or disqualify" — and the time box is at the edge of credible. Two specific edits are blocking; a small bundle of clarifications is non-blocking.
## BLOCKING
**B1. §1.2 Independence matrix: simulated-independence caveat must be declared, not deferred.** The plan's `OPEN:` at line 58 says "If the available people or management planes cannot satisfy the literal `INV-016` predicate, the affected candidate is security-disqualified." But the plan also states the lab has *three hosts administered by one person (Paul)* and assigns witness pairs cross-host (B-W1=`mvmcc03`, B-W2=`mvmcc02`; both are Linux hosts under the same operator and almost certainly share a secret backend and a sudo-capable admin account). The plan never names "one human operator, one directory/IdP admin, one secret-backend admin, one platform admin" — it just lists hostnames. If the lab cannot produce six genuinely independent admin realms, then the appropriate posture is **declared simulated independence** (witnesses are operationally independent in *key custody* and *persistence plane* but share an admin realm), with the consequence that `ADV-30`/`ADV-31` are recognised residuals and the bake-off is honest about not reaching `INV-016` for any candidate. As written, the plan leaves the owner with a binary choice — find six distinct operators (implausible in a 2-week window) or security-disqualify all three — that will likely cause "find the operators" to be answered with "same person wearing different hats", which is precisely the failure mode `INV-016` exists to prevent. **Required change:** add an `OPEN:` that explicitly proposes *simulated independence* as a documented third outcome (alongside "evidence genuine independence" and "disqualify"), names what the residual is, and states that the rubric §7.1 disqualifier (rubric:96, `INV-016`) then does not fire on `ADV-30`/`ADV-31` but is recorded as an expected residual per `TRUST-MODEL.md §12`. The reviewer's NB-5 (`REVIEW-0A1-minimax.md:299`) explicitly flagged this as a *platform-testability* gap; the plan's own `OPEN:` §8 risk row (line 386) acknowledges it in prose but does not bind the consequences to a candidate's gate.
**B2. §1.2 witness-DBA-independence bullet for candidate B is narrower than the `INV-016` predicate.** Rubric §8 (line 146) explicitly lists *"directory/IdP administrator (`ADV-30`), and secret-backend administrator (`ADV-31`)"* in the independence requirement. The plan's §5 B premise table (line 327) rephrases this as *"outside SQL Server, SQL host/cluster, backup platform, DBA credentials, DBA management plane, DBA reporting/failure domain, directory/IdP administration and secret-backend administration"* — good — but the §1.2 *Independence matrix* table for B (lines 51–52) only excludes *"SQL Server/Windows/cluster admins, DBA credentials, SQL backup and DBA management planes"*. The two disagree: §1.2 does not list directory/IdP or secret-backend admin. Since the *Independence matrix* is the operational contract, it must be at least as wide as the §5 B premise row. Opus NB-7 (`REVIEW-0A1-opus.md:155`) raised this exact defect against the rubric itself; the plan inherits the same narrowness. **Required change:** widen B's writer/DBA failure-domain-excluded list in the §1.2 matrix to include directory/IdP admin and secret-backend admin (and align the wording for the other candidates too — AD is Windows-only, but the secret backend is a real shared dependency for all three; `mvmcc03`'s operator can pull `mvmcc02`'s backup key from the shared Vault).
## NON-BLOCKING
**N1. §4.3 one-week credibility is at the edge but defensible.** Five engineer-days per candidate is the rubric's number; the plan's parallelisation argument (one Sol executor per host, one independent observer, plus 2 harness days) does mathematically produce ~7 elapsed days. The plan is right to flag this with `OPEN:` for owner sizing (line 312). Where the plan is weak: it does not account for **Windows executor variability** on `mvmcitest01` (one host hosts B + the Windows/Linux client coverage requirement + the carried `crypto-4` reproduction, all serial on one machine). The "shared/observer activity" column also assumes one observer can witness three parallel fault boundaries (line 56–57 acknowledges this with another `OPEN:` at line 243). Recommendation: pre-record on Day 0 which candidate gets `mvmcitest01` *first* on Days 1–2 in case Windows access slips; do not change the per-candidate budget, but flag that the wall-clock upper bound is closer to 10 days than 7.
**N2. §2.5 invariant map is complete against the rubric's `must-PASS` sets.** I cross-checked every entry in rubric §5 (Adversary table, lines 78–87) against the plan's harness checks. All required invariants appear (e.g., `INV-054` → `CT-LOCK-REREAD-CAS` reaches `SEC-09`, `persist-5/6/10`, `acb-13`; `INV-051` → `APPEND-ACK-DEADLINE-CENSORSHIP` reaches `SEC-01`; `INV-058` → `UNANCHORED-MARKER-PERMANENCE` reaches the dedicated unanchored recovery row). The 15 fully-closed rows named in line 232 match `MATRIX.csv` exactly (verified by grep). One spot: the plan's `INV-018` row (line 205) lists only `STALE-QUORUM-DENY, ROLLBACK-Q3-DENY, OUTAGE-Q3-DENY, RESTORE-WITNESS-RECONCILE` but does not name a separate `ADV-23-ONE-WITNESS` check; the *behavior* is covered (stale/unavailable Q3 denies), but a future reader may want the adversary check name attached. Not blocking.
**N3. §3.1 result isolation when one coordinator runs all three.** The plan handles this correctly via embargo (line 241, 259): executor A does not see B/C measurements until A's security-core package is sealed, shared fixture errata is disclosed symmetrically, and the observer receives witness evidence directly. The §3.1 protocol is sound *if* the coordinator is one Sol lineage rather than one named human. Plan is consistent with the rubric's "no actor id" rule and the executor's "one Sol run per candidate" split (line 238). The residual risk is cross-candidate *pattern* leakage via the shared harness fixtures themselves — the plan's "no weakening of a denial case" rule (line 64) covers this.
**N4. §5 candidate B Developer edition: stated honestly.** The plan does not pre-score B. §5 (line 323) and §6 (line 354) explicitly leave production licensing `OPEN` and withhold B's environment-fit weight and weighted total until it closes. `ASSUMPTION:` (line 331) is correctly labelled. The lab can measure security; it cannot license for production. This is well-handled and matches the rubric §8 requirement.
**N5. No candidate pre-scoring or favouring detected.** The §9 summary (lines 393–395) is symmetric. Section 5's B-premise-validation table applies the rubric §8 checklist, not a softer one. Section 4.2 correctly states extended-row `INCOMPLETE` does not turn a demonstrated invariant failure into incompleteness. The only mild concern is that the §4.3 day-by-day table is *fully* parallel even on Day 1's "Baseline, append, authority" — but since this is the *most predictable* row to parallelise, the plan is right not to be cute.
**N6. What 0C will need that §7 exit criteria may under-specify.** Two gaps I think 0C will trip on:
   (a) The rubric §9 language/stack criteria require evidence of "FIPS/HSM integration: availability and support status of required FIPS-validated cryptographic modules in the actual deployment mode; HSM/KMS/CNG/PKCS#11 integration; key non-exportability...". The plan's §7 handoff (line 374) lists 0C inputs generically but does not call out the **FIPS/HSM evidence** specifically. Without explicit `INV-053` evidence per candidate (e.g., SQL Server EKM, immudb HSM mode, PostgreSQL signing key HSM availability), 0C cannot make the FIPS/HSM criterion decision. The `crypto-4` Windows reproduction is the start, but it is HSM-*unavailable* profile evidence, not HSM-*available* profile evidence. Recommend §7 add a 13th item: "Per-candidate `INV-053` evidence: HSM/KMS/CNG/PKCS#11 availability, key-custody mode, non-exportability claim, argv/diagnostic handling, and the HSM-unavailable profile's re-derived claim cells (rubric §7 last paragraph at rubric:136)."
   (b) The rubric §9 "Portability" criterion requires "deterministic canonicalization and cryptographic behavior across platforms; reproducible builds and conformance results; migration and long-term runtime support". The plan's evidence-package schema (line 100) requires cross-platform client runs but does not require **conformance evidence** (e.g., the same canonical bytes hashed on Windows and Linux produce the same digest under both clients). This is implicit in `INV-001`/`INV-003` but not enforced by a harness check name. Recommend a `CONFORMANCE-CROSS-PLATFORM` check or add it to the existing `PROOF-CONSISTENCY` check.
**N7. Pre-flight checklist (§6) is genuinely complete and load-bearing.** Item 12 (line 350) "Six witness instances provisioned... distinct operators, keys/custody, admin realms, persistence, monitoring, retention and failure domains evidenced" — *this* is the gate that blocks measured results if B1 above is not resolved. Good. The pre-flight does not currently require the simulated-independence declaration proposed in B1; that should be added when B1 is fixed.
**N8. §1.1 three `ASSUMPTION:` blocks (lines 37, 39, 41) are honest but `mvmcc02` capacity is the least pinned.** `mvmcc02`'s 17 GB RAM (line 39) and Docker/Compose support is asserted, not repository-evidenced. The plan correctly labels this as `ASSUMPTION:` but if C's immudb-in-Docker measurement saturates that host, candidate C's results become evidence-of-resource-constraint, not evidence-of-substrate. Recommend the pre-flight checklist (line 348) require a *measured* C startup on `mvmcc02` (with documented memory envelope) before Day 1, so an early "this host cannot run immudb at scale" finding becomes a C-execution rule, not a C-substrate finding.
