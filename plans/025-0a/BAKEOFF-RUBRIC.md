# Phase 0B substrate and anchor bake-off rubric

Status: 0A-5 draft. This rubric defines measurements; it does not contain candidate scores or a substrate decision.

Normative inputs are Plan 025 v3.1 sections 3, 5, 6, and 8; the Phase 0A charter; and `TRUST-MODEL.md` sections 6, 8, and 9. `ADV-*` and `INV-*` identifiers below refer to that trust model.

## 1. Freeze and use rules

1. Freeze this rubric at the 0A exit before collecting any scored 0B measurement. Record the frozen revision, date, reviewers, and owner approval in the 0B results.
2. Run the same mandatory workload, adversary scenarios, fixtures, scale profile, and evidence-capture procedure for A, B, and C. Candidate-specific setup is allowed but must be recorded.
3. Do not change a predicate, weight, workload, or scale after seeing candidate results. A necessary correction requires a new rubric revision, written rationale, and complete rerun of every affected measurement for all candidates.
4. A failed applicable security invariant is disqualifying, not a weighted deduction. Preserve the evidence and identify the failed `INV-*`; do not calculate a weighted total for that candidate.
5. Weighted scoring applies only to candidates that pass every applicable security predicate. Use the evidence anchors and scoring method in section 7; do not substitute an overall impression.
6. A time-box expiration is not a pass. Mark unfinished mandatory work `INCOMPLETE`, which is disqualifying because the applicable invariants were not demonstrated.
7. No candidate is pre-scored. Candidate B is an operational-fit hypothesis whose premises must pass section 8 before environment-fit evidence may receive scoring weight. All three candidates remain security-unproven until measured.

`OPEN:` At the 0A exit, record the frozen git revision, freeze date, two concurring lineages, and owner approval.

## 3. Time box and common controls

`ASSUMPTION:` Allocate at most **5 engineer-days per candidate**, including environment setup, mandatory workload, adversary injection, recovery, evidence packaging, and runbook execution: **15 candidate-days total**. With one executor and one independent observer working sequentially, the elapsed bound is **3 working weeks**; shared harness preparation and final analysis may consume **2 additional engineer-days**, for **17 engineer-days total**. The owner may reduce scope only by revising and re-freezing this rubric before measurement; the mandatory security predicates may not be waived.

Use these common controls:

- Pin candidate product/version, OS, driver, verifier, schema/protocol, witness policy, and deployment configuration before each run.
- Use identical canonical event bytes, authority transitions, revocation ranges, logical history, witness topology, retained prior cuts, and read query mix.
- Use equivalent hardware/resource limits or record and normalize every difference. Do not compare raw throughput across materially different resources without a repeated equal-resource run.
- Run Windows and Linux client/driver exercises for every candidate. The substrate server may use its supported target OS, but verifier and operator workflows must be exercised from both target client platforms.
- Capture commands, configuration digests, timestamps, structured verifier output, proof/checkpoint bytes or digests, witness observations, resource telemetry, and operator elapsed time. Exclude secret values.
- Begin from a separately authenticated genesis policy (`INV-009`) and a signed witness/authority policy (`INV-016`, `INV-036`). Retain a verifier-pinned pre-attack checkpoint outside the writer, database, DBA, and tested witness failure domains.
- Treat malformed, stale, absent, warning, partial, halted, or contradictory evidence as denial rather than PASS (`INV-003`, `INV-006`, `INV-022`).

`OPEN:` Before 0B starts, the owner must approve the event count, payload-size distribution, read concurrency, read/query mix, checkpoint cadence, witness quorum, resource envelope, and recovery-point/recovery-time targets used as the representative scale profile.

## 4. Mandatory falsification workload

The purpose is to falsify security or operability with the minimum common implementation, not to build three production prototypes. Run every row against each candidate within its time box.

| Workload | Procedure | Measurement to record | Pass/fail predicate |
|---|---|---|---|
| Append | Append canonical signed events, including duplicate ids/nonces, a predecessor mismatch, a mutable-row mismatch, and an event with absent or unknown authentication. Include normal and burst rates. | Accepted/denied counts and reasons; committed position/root; append latency p50/p95/p99; throughput; CPU/memory/storage growth; verifier result. | **PASS** only if valid events occupy one unique authenticated order and invalid, duplicate, discontinuous, unauthenticated, or unreconciled events deny without partial PASS (`INV-001` through `INV-005`, `INV-022`). Any silent insertion, deletion, duplicate, mismatch acceptance, or ambiguous authentication is **FAIL**. |
| Rotation | Rotate an authorized signing key, append before and after rotation, then attempt a new action with the superseded key and verify historical events at later cuts. | Transition positions/cuts; old/new key outcomes; cache invalidation; operator steps/time; verifier Q1/Q2 fields. | **PASS** only if authority is evaluated at the authenticated prior position, valid history retains Q1, and the old key cannot perform a new action after loss of permission (`INV-008`, `INV-010` through `INV-012`, `INV-020`). Acceptance based on caller time or stale current-state cache is **FAIL**. |
| Revocation with effect range | At position `r`, issue an authorized dual-control revocation whose effect starts at earlier position `e` and has a finite test end `t`; verify events before, within, and after the range at cuts before and after `r`. Attempt malformed, unauthorized, timestamp-based, self-covering, and out-of-policy ranges. | Issuance decision; bound fields/positions; Q1/Q2 before and after knowledge cut; affected event count; denial reasons; replay time. | **PASS** only if the authorized range deterministically changes Q2 for `e..t` after knowledge cut `r`, preserves Q1/history, leaves positions outside the range unchanged, and denies invalid or unavailable policy (`INV-008`, `INV-012`, `INV-013`, `INV-020`, `INV-028`). Any caller-time authority or unauthorized retroactive effect is **FAIL**. |
| Inclusion and consistency proof | Request proofs for first/middle/last events and growth between retained cuts. Tamper with leaf, path, size, root, range count, filter, schema, and proof bytes; request partial/filtered evidence. | Proof size; generation and local verification latency; malformed-input resource use; result fields and completeness scope. | **PASS** only if valid proofs verify locally and every tampered, ambiguous, oversized, partial-as-complete, or inconsistent proof denies within limits (`INV-003`, `INV-005` through `INV-007`, `INV-014`, `INV-021`, `INV-045`). |
| Checkpoint and witness | Produce signed chained checkpoints at the fixed cadence, distribute them through the candidate design, obtain the pinned witness quorum, and verify from independently retained prior cuts. Withhold one witness and submit a false/stale observation from one witness. | End-to-end checkpoint age; publication/witness latency; quorum result; retained locations/operators; bytes and signatures; alert/refusal latency. | **PASS** only if checkpoints bind required identity/state, witnesses retain signed monotonic observations, quorum respects independent failure domains, and stale/unavailable quorum cannot produce fresh positive Q3 (`INV-014` through `INV-018`). One operator satisfying a multi-witness quorum is **FAIL**. |
| Fork | Present two histories extending one accepted cut to different clients/witnesses; attempt split-view checkpoint publication and later convergence without incident handling. | Which parties observed each cut; detection channel/latency; verifier output; alerts; operator response and retained evidence. | **PASS** only if inconsistent growth or equivocation is rejected and surfaced by local retained cuts or required witnesses; it may not be silently repaired or aggregated to PASS (`INV-005`, `INV-014` through `INV-018`, `INV-021`, `INV-022`). An undetected fork below the declared non-resisted quorum is **FAIL**. |
| Rollback: old DB plus old checkpoint | After newer checkpoints are independently retained, replace the live database and its locally available checkpoint with a mutually consistent older pair. Attempt reads, appends, and positive Q3 claims before recovery. | Old/new cuts; first detection point/latency; denied operations; alert; recovery steps; source of expected cut. | **PASS** only if the verifier learns the expected cut from pinned/local independent state, rejects stale substitution, and withholds fresh positive Q3 and authority-bearing actions until consistent recovery (`INV-011`, `INV-017`, `INV-018`, `INV-022`, `INV-038`, `INV-049`). Acceptance of the self-consistent old pair is **FAIL**. |
| Restore | Restore a backup to clean infrastructure after advancing beyond the backup cut. Verify artifacts/profile, reconcile from an external retained cut, replay authority, reconcile witnesses, and resume operation. Also attempt to resume before all checks complete. | RPO/RTO; operator touch time; steps and errors; restored and recovered cuts; proof/replay duration; first allowed write; witness status. | **PASS** only if premature operation denies and restored service is accepted after artifact/profile verification, full consistency from retained external state, authority replay, witness reconciliation, and projection equivalence (`INV-017`, `INV-018`, `INV-035` through `INV-038`, `INV-049`). |
| Projection rebuild | Corrupt/delete mutable projection rows, then rebuild from authenticated source evidence at a fixed cut/policy. Compare to the pre-corruption canonical projection and repeat after revocation. | Row/digest differences; rebuild duration/throughput; resource peak; cut/policy inputs; mismatch/refusal output. | **PASS** only if mutable fields cannot grant authority, a fresh rebuild is deterministic and equal at the same cut/policy, and any source inconsistency denies (`INV-004`, `INV-007`, `INV-012`, `INV-038`, `INV-039`). |
| Representative read volume | Run the frozen query mix at the frozen volume/concurrency in healthy state, stale-checkpoint state, witness outage, and post-rotation/revocation state. Verify bounded proofs locally on sampled and policy-required reads. | p50/p95/p99 latency; throughput; error/deny rate; CPU/memory/network; proof/cache hit rates; checkpoint age; stale-result count; Windows/Linux driver behavior. | **PASS** only if every result remains bound to evidence/root/policy/cut, cache invalidation and freshness rules hold, stale or unavailable Q3 is represented honestly, and no partial/unknown result becomes PASS (`INV-007`, `INV-011`, `INV-012`, `INV-018` through `INV-023`, `INV-045`, `INV-049`). Performance has no security override. |

## 5. Mandatory adversary scenarios

|---|---|---|---|

## 7. Eligibility and scoring

### 7.1 Disqualifying invariant gate

A candidate is eligible for weighted scoring only when all mandatory workload and adversary rows pass every cited applicable invariant. Any of the following disqualifies it:

- A demonstrated applicable `INV-*` failure.
- Inability to complete a mandatory security test reproducibly inside the time box.
- A witness design that does not place the required quorum in failure domains independent of the writer and DBA (`INV-016`).
- Rollback to an old database plus old checkpoint producing a fresh positive Q3 result (`INV-017`, `INV-018`).
- Restore or break-glass resuming ordinary operation without the required re-verification and reconciliation (`INV-038`, `INV-049`).
- Dependence on a centralized unauthenticated/self-authenticated verdict where local proof verification is required (`INV-019` through `INV-023`).

Security passes are not points and do not enter the weighted total.

### 7.2 Weighted criteria

For an eligible candidate, score each criterion from 0 to 5 using the evidence anchors below. Weighted points are `criterion weight * score / 5`, totaling 100 maximum. Publish each raw score, evidence reference, and calculation. Ties remain ties unless 0C defines and freezes a tie-break rule before opening results.

| Criterion | Weight | Evidence and anchors |
|---|---:|---|
| Operational sustainability and witness independence | 25 | Staffing coverage; number and independence of operators/failure domains; monitoring and alert ownership; checkpoint cadence/retention; routine operator touch time; documented, rehearsed verification and incident runbooks. `0` = not operable or independence absent; `1` = heroic/manual and unowned; `3` = named roles and repeatable runbooks with material gaps; `5` = independently operated, monitored, rehearsed, and sustainable under the target staffing model. |
| Recovery, degraded state, and break-glass operability | 20 | Measured RPO/RTO; restore success; external-cut reconciliation; projection rebuild; outage refusal; dual-control emergency flow and audit closure. `0` = unsafe/incomplete recovery; `1` = manual recovery cannot demonstrate consistency; `3` = successful recovery with notable manual risk or target miss; `5` = repeatable target-meeting fail-closed recovery with complete re-verification. |

| Platform integration and driver ergonomics | 15 | Reproduced install, authentication, connection, proof-verification, diagnostics, and upgrade workflows on both Windows and Linux clients; target server/HA integration. `0` = a required platform cannot operate; `1` = unsupported/custom fragile path; `3` = supported path with material friction; `5` = supported, automated, diagnosable path on both platforms. |

## 10. 0B result record

For each candidate, the result must contain:

- Frozen rubric revision and common-fixture/configuration digests.
- Candidate versions, topology, resources, licenses, operators, trust/failure domains, and deviations.
- One evidence reference and verdict for every section 4 workload row and section 5 adversary row.
- An invariant-gate result listing each tested `INV-*` as `PASS`, `FAIL`, or `INCOMPLETE`, with reproduction evidence.
- The completed operational-requirements row and candidate B premise checklist where applicable.

The 0B record supplies evidence to 0C. It does not change this frozen rubric and does not itself select the language/stack.
